# hal_capabilities — what a plugin needs before it can answer anything

A plugin being *built* says nothing about whether it can say anything about the
netlist in front of you. `dataflow_analysis` needs sequential gate types;
`xilinx_toolbox` needs a Xilinx library; `hawkeye` needs `graph_algorithm` loaded
first. Today that knowledge lives in READMEs and in the heads of the people who
wrote the plugins, and the failure mode is an analysis that runs, finds nothing,
and gets read as *nothing there*.

`hal_capabilities` makes it declarative. Each plugin ships a `capabilities.json`,
validated against a versioned schema, naming its plugin dependencies, the
gate-type properties and pin types it reads, the gate libraries it has been
exercised against, and what it costs to run. The discovery command then answers
four questions instead of one.

## Four states, not one

```bash
python tools/hal_capabilities --build-dir <build> list --probe --netlist <netlist>
```

```
plugin            declared  built  loadable  netlist
----------------  --------  -----  --------  ---------
example_analysis  yes       yes    yes       supported
graph_algorithm   no        yes    yes       -
hawkeye           no        no     no        -
```

| state | means | needs |
| --- | --- | --- |
| `declared` | the plugin ships a `capabilities.json` | nothing |
| `built` | its shared object is in `<build>/lib/hal_plugins/` | `--build-dir` |
| `loadable` | `plugin_manager` instantiated it and `hal_plugins.<name>` imported | `--probe` and a built HAL |
| `supported` / `partial` / `unsupported` | it can say something about *this* design — or exactly why not | `--netlist` |

`partial` is a real answer: the analysis runs, but some gate types it matched are
missing something it needs, so its result will have named holes.

## Command line

```bash
python tools/hal_capabilities list                      # source tree only
python tools/hal_capabilities --build-dir <build> list --probe
python tools/hal_capabilities show  example_analysis
python tools/hal_capabilities check example_analysis --netlist <netlist>
python tools/hal_capabilities validate                  # every plugins/*/capabilities.json
python tools/hal_capabilities schema --path
```

Exit codes: `0` supported (or `partial`), `1` invalid declaration or failure,
`3` unsupported for this netlist, `4` a declared dependency is missing or the
plugin does not load.

## The declaration

`plugins/<name>/capabilities.json`, generated by `tools/new_plugin.py`:

```json
{
  "capabilities_version": "1.0.0",
  "plugin": {"name": "my_analysis", "version": "0.1", "kind": "analysis",
             "description": "...", "build_option": "PL_MY_ANALYSIS"},
  "dependencies": {"plugins": ["graph_algorithm"]},
  "requires": {
    "gate_type_properties": {"all_of": ["sequential"]},
    "gate_type_pin_types": ["clock"],
    "netlist": {"min_gates": 1, "needs_gate_library": true}
  },
  "supported_gate_libraries": {"mode": "any", "verified": ["EXAMPLE_GATE_LIBRARY"]},
  "findings": {"schema_version": "1.0.0", "statuses": ["heuristic", "unsupported"]},
  "resources": {"complexity": "linear in the number of gates", "deterministic": true}
}
```

Validation is two layers. The schema checks the shape; `validate.semantic_errors`
checks what a schema cannot — that every named `GateTypeProperty` and `PinType`
is one HAL actually has (a typo would otherwise mean "unsupported forever, for a
reason nobody can act on"), that an allow list is not empty, that a plugin
claiming library independence does not also carry a list, and that an analysis
declares which findings statuses it can emit.

## No drift

The declaration is the single source of truth, used twice: the plugin's
`CMakeLists.txt` compiles it into the shared object
(`<Name>Plugin::get_capabilities()`) and copies it to
`<build>/share/hal/plugin_capabilities/<name>.json`. `list --probe` compares the
compiled-in copy, `get_dependencies()` and `get_version()` against the source
tree and reports any disagreement as a defect — a stale build and a stale
declaration look different, and both are worth knowing about.

## Layout

```
schema/plugin-capabilities-1.0.0.schema.json  the normative schema (JSON Schema 2020-12)
schema.py                                     version constants and schema lookup
validate.py                                   schema + closed-vocabulary validation
support.py                                    declaration x netlist -> supported/partial/unsupported
discover.py                                   declared / built / loadable, drift, dependencies
cli.py, __main__.py                           the command
test_hal_capabilities.py                      unit tests (no HAL needed)
```

Only `discover.probe_loadable` and the CLI's `--netlist` handling need a built
HAL; they reach it through `hal_viz.halenv`. Validation reuses
`hal_findings.jsonschema_mini`, so the whole package runs on a plain interpreter
with the standard library only. When `jsonschema` *is* installed,
`validate --jsonschema` and the tests cross-check the two.

## Tests

```bash
python -m unittest discover -s tools/hal_capabilities -t tools -p "test_*.py"
```

The netlist in those tests is a handful of stub objects shaped like the `hal_py`
bindings. What they cannot cover — that a real plugin loads and that its
compiled-in declaration still matches — is
`tests/headless_smoke/plugin_scaffold_smoke.py`.

## Versioning

`capabilities_version` is mandatory and validated; a document with an unknown
version is rejected outright rather than parsed on a best-effort basis. Add a new
`schema/plugin-capabilities-<version>.schema.json` and extend
`SUPPORTED_CAPABILITIES_VERSIONS` when the shape changes; never edit a released
schema file in place.

See also: [`documentation/plugin_development.md`](../../documentation/plugin_development.md)
for the contributor walkthrough, and [`tools/hal_findings`](../hal_findings/README.md)
for the result contract.
