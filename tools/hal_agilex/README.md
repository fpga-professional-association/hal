# hal_agilex — validated Altera Agilex primitive support

Loading a vendor netlist is not the same as understanding it. This package
exists so that "HAL supports Agilex" can only mean something checkable: a real
Quartus export, a primitive coverage list that is small and explicit, semantics
that are validated against the export they claim to describe, and everything
outside that list reported as a machine-readable gap instead of being quietly
imported.

Everything except `hal_adapter.py` runs on a plain Python 3 interpreter with the
standard library only — no HAL build, no Quartus installation — so the primitive
semantics, the reader, the reference simulator, the coverage inventory and the
recognition adapter are all testable anywhere.

## The representative export

| | |
| --- | --- |
| family | **Agilex 3** (the family the issue prefers; installed and licensed on the machine the fixtures were made on) |
| device | **A3CW135BM16AE6S**, package MBGA896 |
| tool | **Quartus Prime Pro Edition 26.1.0 Build 110 03/26/2026 SC** |
| flow | `quartus_syn <rev> -c <rev>` then `quartus_eda --simulation --format=verilog --tool=questasim --output_directory=simulation <rev> -c <rev>` |
| stage | post-**synthesis** (the *synthesized* snapshot; no fitting, so no placement noise in the fixture) |
| families offered by this install | Agilex 7, Agilex 3, Agilex 5 (`quartus_sh -t` / `get_family_list`) |

Pro Edition 26.1 no longer offers a VQM writer for these families; the EDA
netlist writer's Verilog output (`.vo`) is the export the flow produces, and it
is what the fixtures contain. Each fixture directory carries a `MANIFEST.json`
with the exact device, version, commands, per-file SHA-256 and regeneration
steps, plus a `GROUND_TRUTH.md` stating what the export contains and what the
tooling must report for it.

**Redistribution.** The committed `.vo` files are tool output generated from
FPGAPA-authored RTL; the Altera copyright header `quartus_eda` writes is kept
verbatim. No vendor simulation models, device databases or encrypted libraries
are redistributed — notably *not* `eda/sim_lib/fmica_atoms_ncrypt.sv`, the
encrypted Agilex atom models, which are neither used nor included. Anyone with
a Quartus Pro installation can regenerate every fixture from the commands in its
manifest.

## Coverage: what is modelled, and what is not

| primitive | status |
| --- | --- |
| `tennm_lcell_comb` | **modelled** — normal mode (`combout`) and arithmetic mode (`sumout`, `cout`), with `extended_lut = "off"`, `shared_arith = "off"`, `datag`/`datah`/`sharein` tied off |
| `tennm_ff` | **modelled** — synchronous capture under `ena`, asynchronous active-low `clrn`, with `aload`/`sload`/`sclr`/`sclr1` tied to 0 and `devclrn`/`devpor` released |
| `tennm_ram_block`, `tennm_mac`, PLL/transceiver/IO and everything else | **not modelled**, reported as `unsupported` findings with a reason per type |

The two modelled cells are also modelled only in the configurations above. An
instance that uses `sclr`, the fracturable 7-input mode or shared arithmetic is
*out of coverage* and is reported — never given the modelled behaviour because it
happens to be the same gate type.

### The ALM mask decoding this rests on

```
combout = lut_mask[ a + 2b + 4c + 8d + 16e + 32f ]

f0     = lut_mask[      a + 2b + 4c + 8d ]     (bits  0..15)
f1     = lut_mask[ 16 + a + 2b + 4c + 8d ]     (bits 16..31)
sumout = f0 XOR cin
cout   = (f0 AND cin) OR (NOT f0 AND f1)
```

This is not asserted from memory. It is the form Quartus itself prints next to
every arithmetic instance in the export (`// Equation(s):`), and it is what makes
the exported counter simulate identically to its RTL — see below.

## How the claims are validated

| claim | how it is checked | status it earns |
| --- | --- | --- |
| the primitive semantics are right | simulate the *exported netlist* with these semantics and compare against a Python model of the *RTL it was synthesised from* (`fixtures/*/reference.py`) | `proven_bounded` (200 cycles) for the counter, `proven_under_assumptions` (all 64 vectors) for the combinational fixture |
| the import rewrite is exact | simulate the original and the rewritten netlist side by side and require identical outputs | unit tests |
| the recognized adder really adds | drive both operands over all 65 536 assignments and compare against `A + B` | `proven_under_assumptions` |
| the pattern match itself | structural evidence only | `heuristic` |
| uncovered primitives | enumeration | `unsupported`, with counts and reasons |

Every document is a `hal_findings` document and is validated against the shared
schema in the test suite.

## The gate library

`plugins/gate_libraries/definitions/AGILEX_TENNM.hgl` is generated by
`library.py` (a test asserts the committed file matches the generator, and
`hal_agilex library --check` does the same from the command line).

`tennm_ff` carries a full `ff_config`: `next_state = (ena & d) | (IQ & !ena)`,
`clocked_on = clk`, `clear_on = !clrn`.

`tennm_lcell_comb` deliberately carries **no** `lut_config` and no Boolean
function. HAL derives a LUT function from an init string only for gate types
with at most six input pins and one function per LUT output; the ALM has ten
input pins and three outputs whose meaning depends on `lut_mask` *and* on the
mode, so a `lut_config` here would make `Gate::get_lut_function` log an error and
return an empty function. Instead `hal_adapter.elaborate()` attaches the
per-gate functions with `Gate.add_boolean_function` after loading — and attaches
nothing at all to a gate outside the coverage, so an analysis that reads it sees
a free variable rather than a wrong one.

`HAL_GND`/`HAL_VCC` are not Quartus atoms: HAL's Verilog parser needs a ground
and a power gate type to materialise the `1'b0`/`1'b1` literals the export uses.
The names are prefixed so they cannot be mistaken for vendor primitives.

## The import rewrite

HAL's Verilog parser is a structural netlist reader and rejects three things the
Quartus writer emits. `vo_import` handles each one exactly or refuses:

* `tri1 devclrn/devpor/devoe` become wires with `assign … = 1'b1`;
* `.datac(~x)` inversions are **absorbed into `lut_mask`** (mask bit `j` moves to
  `j ^ (1 << i)`, an exact relabelling). An inversion on `cin`, `sharein`, a
  flip-flop pin or a `datae`/`dataf` of an arithmetic cell is refused, because
  absorbing it would change the meaning;
* unconnected pins (`.combout()`) are dropped, and the `assign unknown = 1'bx`
  that Quartus declares is dropped only while nothing reads it.

A netlist containing any uncovered primitive is refused outright, with the list
of offending types.

## Command line

```bash
python tools/hal_agilex inventory  export.vo [-o findings.json] [--strict]
python tools/hal_agilex import     export.vo -o export.hal.v
python tools/hal_agilex behavior   export.vo --reference reference.py
python tools/hal_agilex recognize  export.vo
python tools/hal_agilex fixture    tools/hal_agilex/fixtures/agilex3_counter_adder
python tools/hal_agilex library    --check
python tools/hal_agilex elaborate  export.hal.v --gate-library plugins/gate_libraries/definitions/AGILEX_TENNM.hgl --hal-lib <build>/lib
```

Exit codes: `0` success, `1` failure, `2` with `--strict` when the findings
contain a counterexample, an error or an unsupported result.

## Layout

```
primitives.py     the modelled semantics and the coverage predicates
vo_netlist.py     reader for the Quartus .vo subset (refuses what it cannot read)
simulate.py       reference simulator over the modelled primitives
behavior.py       netlist-versus-RTL validation -> findings
inventory.py      primitive inventory and coverage -> findings
recognize.py      architecture dispatch + carry-chain adder/counter -> findings
vo_import.py      rewrite a .vo into HAL-readable Verilog
library.py        generator for plugins/gate_libraries/definitions/AGILEX_TENNM.hgl
hal_adapter.py    the only module that needs hal_py: load + attach semantics
cli.py, __main__.py
fixtures/         three exports with manifests, ground truth and reference models
test_hal_agilex.py       unit tests (no HAL, no Quartus)
test_hal_agilex_hal.py   integration tests (needs a built HAL)
```

## Tests

Without HAL, from the repository root:

```bash
python -m unittest discover -s tools/hal_agilex -t tools -p "test_hal_agilex.py"
```

35 tests, about 8 seconds. With a built HAL (inside the build container):

```bash
export HAL_PY_PATH=/opt/hal/build/lib
export HAL_BASE_PATH=/opt/hal/build
python -m unittest discover -s tools/hal_agilex -t tools -p "test_*_hal.py"
python tools/hal_agilex elaborate \
    tools/hal_agilex/fixtures/agilex3_counter_adder/counter_adder.hal.v \
    --gate-library plugins/gate_libraries/definitions/AGILEX_TENNM.hgl \
    --hal-lib /opt/hal/build/lib
```

## Integration notes

* The gate library is a new file in `plugins/gate_libraries/definitions/`, which
  that plugin's CMake glob picks up automatically and copies into
  `share/hal/gate_libraries/`; no existing file was touched. That directory's
  `.gitignore` ignores everything by default — "require explicit add of
  unfinished libraries" — so `AGILEX_TENNM.hgl` was committed with `git add -f`,
  which is the explicit add that policy asks for.
* Findings use `tools/hal_findings` (schema 1.0.0) throughout, so results drop
  straight into whatever consumes findings documents elsewhere in the fork.
* `module_identification` has per-architecture recognizers under
  `plugins/module_identification/src/architectures/`. The recognizer here is
  intentionally a Python one on the export level: it needs no build, it can be
  validated exhaustively, and it produces findings rather than plugin-internal
  candidates. If the arithmetic recognition later moves into
  `module_identification`, `recognize.classify_arithmetic_cell` and the chain
  walk are the pieces to port, and the fixtures here are the tests to port with
  them.

## Limits, stated plainly

* One family (Agilex 3), one device, one Quartus version, one export stage. A
  post-fit export, another family or another version has not been looked at.
* Two primitives, in one configuration each.
* The reference comparison is two-valued: no x/z propagation, no timing, no
  power-up state (`power_up = "dont_care"` in the export is not modelled;
  registers start at 0).
* The 200-cycle sequential check is a bound, not a proof, and is reported as
  `proven_bounded` for exactly that reason.
* `hal_adapter` has been written against the current bindings but, like anything
  needing a HAL build, is exercised only in the container.
