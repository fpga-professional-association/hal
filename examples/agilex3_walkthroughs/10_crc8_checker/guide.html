Reverse-engineering an Agilex 3 netlist

Walkthrough 10 — a serial CRC-8 checker: from a Quartus Prime Pro export back to RTL, one command at a time.

Device A3CW135BM16AE6S (Agilex 3, package MBGA896) · Quartus Prime Pro 26.1.0 Build 110 · post-synthesis export · HAL with AGILEX_TENNM.hgl · 13 gates, 8 flip-flops, 5 ALMs.

Who this is for. An engineer who can read Verilog but has never taken a gate-level netlist apart. 1. The design (the answer key)

The target is a serial CRC-8 checker. Bits arrive one per enabled clock, most significant bit first; the remainder register divides the incoming bit stream by a generator polynomial, and a flag says whether the remainder is currently zero. Shift in message ‖ crc(message) and the remainder ends at zero — that is how a receiver decides a frame is intact.

spec.md states the intended behaviour; design.v is the RTL that was handed to Quartus. Read them now if you like, then forget them: from section 2 onwards the walk uses only the netlist.

module crc8_checker (
    input  wire       clk,      // single clock domain
    input  wire       rst_n,    // asynchronous, active low: start of frame
    input  wire       en,       // consume one serial bit this cycle
    input  wire       din,      // serial data, MSB first
    output wire [7:0] crc,      // running remainder
    output wire       match     // remainder == 0  ->  codeword accepted
);

    localparam [7:0] POLY = 8'h07;          // x^8 + x^2 + x + 1

    reg [7:0] crc_r;
    wire feedback = crc_r[7] ^ din;

    always @(posedge clk or negedge rst_n) begin
        if (!rst_n) begin
            crc_r <= 8'h00;
        end else if (en) begin
            crc_r[0] <= feedback;                        // x^0 term, always set
            crc_r[1] <= crc_r[0] ^ (feedback & POLY[1]); // POLY[1] = 1 -> tapped
            crc_r[2] <= crc_r[1] ^ (feedback & POLY[2]); // POLY[2] = 1 -> tapped
            crc_r[3] <= crc_r[2] ^ (feedback & POLY[3]); // POLY[3] = 0 -> shift
            crc_r[4] <= crc_r[3] ^ (feedback & POLY[4]);
            crc_r[5] <= crc_r[4] ^ (feedback & POLY[5]);
            crc_r[6] <= crc_r[5] ^ (feedback & POLY[6]);
            crc_r[7] <= crc_r[6] ^ (feedback & POLY[7]);
        end
    end

    assign crc   = crc_r;
    assign match = (crc_r == 8'h00);

endmodule
The one fact worth carrying POLY = 8'h07 = 8'b0000_0111, so exactly three of the eight next-state equations contain feedback: bits 0, 1 and 2. Five are a plain shift. That asymmetry is the polynomial, and recovering it from thirteen gates is what sections 5 and 6 of the walk do.

Why this design, and not something bigger

The RTL is deliberately constrained so that the whole post-synthesis netlist lands inside what this repository has actually validated: one clock, no vendor IP, no RAM, no DSP, no PLL, no instantiated IO buffers. What is left is tennm_lcell_comb (the Agilex ALM) and tennm_ff — the two primitives plugins/gate_libraries/definitions/AGILEX_TENNM.hgl models and tools/hal_agilex validated against a real export. A design that pulls in an unmodelled primitive does not get quietly imported here: it gets refused, with the offending type named.

What an ALM actually is tennm_lcell_comb is not a 4-input LUT with a truth table you can read off. It has ten input pins and three outputs, and what it computes depends on lut_mask and on the mode. In normal mode the rule is combout = lut_mask[a + 2b + 4c + 8d + 16e + 32f]; in arithmetic mode the mask splits into a propagate half and a generate half feeding the carry chain. This walkthrough's design uses normal mode only. That decoding is not folklore: Quartus prints the equivalent equation next to every instance (the // Equation(s): comment above), and tools/hal_agilex validates it by simulating the export against a Python model of the RTL.

2.4 make it loadable by HAL

$ python tools/hal_agilex import netlist/crc8_checker.vo -o netlist/netlist.hal.v

HAL's Verilog front end is a structural netlist reader and rejects three things the Quartus writer emits. The importer handles each one exactly, or refuses:

  • tri1 devclrn/devpor/devoe become wires with assign … = 1'b1;
  • inversions written on data pins (.dataa(~crc_r[0])) are absorbed into lut_mask — mask bit j moves to j ^ (1 << i), an exact relabelling. The ALM quoted above is exactly this case: the export writes lut_mask 64'h6969696969696969 with ~crc_r[0], ~crc_r[7] and ~din on its data pins, and the imported file writes lut_mask 64'h9696969696969696 with the same three nets uninverted. Both are the 3-input XOR the equation comment describes — inverting an odd number of inputs of an XOR just complements it, and complementing the mask is what the relabelling does. An inversion on cin, on a flip-flop pin, or on datae/dataf of an arithmetic cell is refused instead, because absorbing it would change the meaning;
  • unconnected pins (.combout()) are dropped, and the assign unknown = 1'bx Quartus declares is dropped only while nothing reads it.

$ python tools/hal_agilex --strict inventory netlist/crc8_checker.vo -o artifacts/inventory.findings.json

3. Making it a fair fight

Quartus is generous to a reverse engineer. Look at what survived synthesis in netlist.hal.v: a bus called crc_r[7:0], an instance called feedback, another called reduce_nor_0. If you were allowed to use those, this walkthrough would be one paragraph long and would teach nothing. Real targets — obfuscated netlists, netlists recovered from a bitstream, anything built with name mangling on — do not have them.

So the walk runs on netlist.anon.hal.v, produced by anonymize.py:

$ python anonymize.py netlist/netlist.hal.v netlist/netlist.anon.hal.v

Removed

  • the module name, every port name, every net name, every instance name;
  • the internal wire [7:0] declaration — its bits become eight unrelated scalar wires, so the register bank does not arrive pre-grouped;
  • the emission order — instance and net numbering are scrambled by a fixed permutation, so u0…u12 says nothing about the design.

Kept, because you really would have it

  • gate types and pin names (tennm_ff.clk, .ena, .clrn) — those come from the device, not the design;
  • lut_mask, extended_lut, shared_arith;
  • the connectivity, exactly;
  • top-level port direction, width and bus grouping: package pins really are grouped and ordered.
Be honest about the leftovers Keeping the output bus port_o0[7:0] is a real hint: it tells you eight signals belong together and in what order. We keep it because a physical target gives you that too, and because it lets the walk cross-check an answer it derives independently (step 6 recovers the same bit order from the logic alone and the two agree). If your target has no such bus, the chain walk in step 6 still works — you just lose the confirmation.

Everything below is run against the anonymised copy. Every command shown also works on netlist.hal.v; check.py runs the whole walk on both and asserts they yield the same polynomial.

5. The walk, step by step

Each step is one command, the output it printed, and the reasoning that turns that output into a conclusion. The commands are subcommands of re_walk.py — which contains no knowledge of the design: the port roles, the bit order, the tap set, the reset value and the polynomial are all derived, and the script fails loudly rather than assuming, if the structure does not fit — plus the general-purpose tools in tools/.

Reasoning Three of the four inputs go only to control pins, and each to exactly one kind: one drives eight clk pins, one drives eight clrn pins, one drives eight ena pins. That pins down three port meanings with no ambiguity at all — and it also tells you the design is single-clock with a single asynchronous reset domain, so there is no CDC problem to chase. What this does not tell you Nothing here says the reset is used as "start of frame" rather than "power-on init", and nothing says en means "a data bit is valid" rather than "run". Port roles are structural; port intent is not recoverable from a netlist, and a good report says so.

2 Find the state

Cut the design at the register boundary. Everything else is combinational logic between registers, and it is far easier to read once you know what the state is.

Reasoning

One control signature, eight flip-flops. Grouping registers by (clk, clrn, ena) is the cheapest structural clustering there is, and here it puts all eight in one bucket. Eight registers that start together, stop together and clear together are almost always one architectural object — a word — not eight unrelated bits.

Five of eight take their D straight from another flip-flop's Q. That is a shift register: no logic in between, just a hop. The other three have an ALM in the path. A pure shift register would have all eight like that, and a counter would have arithmetic cells (an ALM carry chain) instead — so this is neither. Something is being folded into the shift at three specific places, and finding out what is the rest of the job.

Reasoning

A pipeline is a chain: its SCCs are all singletons, because data never comes back. Here every flip-flop and the ALMs between them sit in one strongly connected component, so the last stage feeds back into the first. A shift register whose output is fed back through XOR gates is an LFSR, and an LFSR with an external data input mixed into the feedback is a CRC. This is where the hypothesis is born; the next three steps are what turn it into a claim you can defend.

Generalising: SCC analysis is the standard first cut on unknown sequential logic. Singleton SCCs = pipeline/datapath. One big SCC over a register bank = counter, accumulator, LFSR or FSM state. Several medium SCCs = several such objects, and the component boundaries are a free partition of the design.

5 Read the logic algebraically, not visually

Now the part that actually decides the case. For each flip-flop, take the net on its d pin and push the Boolean function of every ALM in front of it backwards until nothing is left but flip-flop outputs and primary inputs. HAL does the symbolic work: hal_agilex.hal_adapter.elaborate() attached a BooleanFunction to each ALM from its lut_mask, and BooleanFunction.substitute() composes them.

Reasoning

Do not eyeball these expressions — test them. The script enumerates each function's truth table over its support and asks a single question: is it affine over GF(2), i.e. a constant XOR a subset of its inputs? That test is exact and mechanical (evaluate at 0, at each unit vector, then verify all remaining assignments), and it turns a pile of sum-of-products into a one-line statement per register.

All eight came back affine with constant term 0. A state machine whose next state is a linear map over GF(2) is exactly the definition of an LFSR — no more hand-waving from the picture in step 3. And every constant term being 0 is the statement "no stage is inverted", which is what fixes the reset value at 0x00 rather than 0xFF.

Why this scales Affinity is a cheap, decisive property. On a bigger unknown design, running the same test over every next-state function partitions the registers into "linear" (LFSRs, scramblers, CRCs, Gray-ish counters) and "not linear" (adders, FSM encodings, comparators) before you have understood a single one of them.

6 Recover the polynomial

Eight linear equations. Turning them into "CRC-8, polynomial 0x07" is four mechanical deductions, and the script does exactly these:

  1. Which input is the data? The one primary input that appears in a next-state function at all. (The clock, reset and enable do not appear — they are not data, they are the register's own semantics.)
  2. Which register is the feedback? Take the next-state functions that contain the data bit and intersect their register supports. Exactly one register survives: it is xored in wherever the data bit is, so data XOR that register is a single shared feedback term.
  3. What is the bit order? Strike the feedback term and the data bit out of every equation. What remains is at most one register per equation — its shift predecessor. One equation has nothing left: that is bit 0. Follow the successors and you have the chain, and the chain must end at the feedback register (a closed loop), or the LFSR hypothesis was wrong.
  4. What are the taps? The chain positions whose equation contains the data bit. In this Galois-form CRC the tapped positions are the set bits of the generator polynomial's low byte.

Reasoning The function is 1 for exactly one of the 256 states — the all-zero one — and 0 for the other 255. That is not a heuristic label, it is the entire truth table. So this output is state == 0. On a CRC that is the standard "remainder is zero, the codeword checks out" flag, which is the first piece of purpose (rather than structure) the netlist has given up.

Structurally it is an 8-input NOR that did not fit in one ALM: a 4-input NOR (lut_mask 64'h0001000100010001, the mask has a single set bit per 16-bit window, i.e. "all four inputs low") feeding the fifth input of a second cell that ANDs it with a NOR of the remaining four (64'h0001000000010000). Splitting a wide gate across cells is routine, and it is why counting gates tells you nothing about the design's intent.

6. Reconstruction, and what was lost

recovered.v is the RTL written from the netlist alone. Every line carries the observation it came from:

module recovered_crc8 (
    input  wire       clk,        // port_i1: the only net reaching all 8 tennm_ff .clk pins
    input  wire       rst_n,      // port_i2: the only net reaching all 8 .clrn pins;
                                  //          tennm_ff models clrn as ASYNCHRONOUS and
                                  //          ACTIVE LOW, so this is an async reset to 0
    input  wire       en,         // port_i3: the only net reaching all 8 .ena pins
    input  wire       din,        // port_i0: reaches only ALM data inputs, never a
                                  //          control pin -- the serial data bit
    output wire [7:0] state,      // port_o0: driven straight by the 8 register outputs
    output wire       zero_flag   // port_o1: truth table over `state` is exactly state==0
);

    localparam [7:0] POLY = 8'h07;

    reg [7:0] q;
    wire feedback = q[7] ^ din;

    always @(posedge clk or negedge rst_n) begin
        if (!rst_n) q <= 8'h00;
        else if (en) q <= {q[6:0], 1'b0} ^ (feedback ? POLY : 8'h00);
    end

    assign state     = q;
    assign zero_flag = ~|q;

endmodule

Recovered exactly

FactEvidence
8-bit state register, async active-low clear to 0x00, clock-enabled gate types + pin connectivity + the tennm_ff model; constant term 0 in every next-state function
Port roles: clock, async reset, enable, serial data, state out, flag out which pin kinds each net reaches (step 1); truth table of the flag (step 7)
The state update is linear over GF(2) exhaustive affinity test on all eight functions (step 5)
Galois-form CRC, feedback from bit 7, taps at 0/1/2, polynomial 0x07 the four deductions of step 6
Bit order of the word derived from the chain (step 6) and independently confirmed by the output bus indices
It really computes CRC-8/SMBUS simulating the netlist on "123456789" gives 0xF4 (step 8)

Lost for good

LostWhy, and what you can do about it
Every name. crc8_checker, crc_r, match, POLY, feedback, the port names. Names are metadata; synthesis is free to keep, mangle or drop them, and a hostile flow drops them. Here they were kept by Quartus and deliberately thrown away (section 3). Nothing in a netlist can give them back — you name things after what you proved they do.
Hierarchy. The export is one flat module. Synthesis flattened it. On a larger design you rebuild an approximate partition from SCCs, register banks and cone boundaries — that is a reconstruction, not a recovery, and should be labelled as one.
Coding style. design.v writes eight explicit next-state equations; recovered.v writes a shift and a conditional XOR. They synthesise to the same 13 cells. The netlist is an equivalence class, and every member of it is an equally correct answer.
Intent. That rst_n means "start of frame", that en means "a bit is valid", that the flag is meant to gate a frame acceptance. Not in the netlist, not derivable, and the most common place for RE reports to overclaim. State the structure; label the intent as a guess.
The parameter POLY as a parameter. Constants are folded at elaboration. You recover the value 0x07 from the tap positions; that it was once a localparam is unknowable.
Initial/power-up state, timing, and x-propagation. The export says power_up = "dont_care", and the model here is two-valued with no timing. The reset value 0x00 is recovered from the clear path, not from power-up.
One thing this walkthrough did not have to do Every gate in this netlist was inside the validated coverage, so every ALM had a real Boolean function. On a design with a RAM, a DSP block or an ALM in a mode hal_agilex does not model, those gates get no function, and the substitution in step 5 stops at them with an error rather than inventing something. That is the correct behaviour and you should expect to hit it: the workaround is to treat the unmodelled block as a black box with named inputs and outputs, recover what surrounds it, and validate the box separately.

7. Going further

  • Change the polynomial and re-run. Edit design.v (POLY = 8'h1D, say), redo section 2, and watch step 6 report the new tap set without a single change to the analysis. That is the test of whether a recovery script actually derives things.
  • Break the assumption. Add a synchronous load of a non-zero seed. Quartus will start using sload/sclr, which are outside the modelled coverage — so hal_agilex will refuse the flip-flop rather than model it wrongly, and you get to see what a coverage gap looks like from the analysis side.
  • Try the parallel form. A byte-at-a-time CRC computes eight LFSR steps combinationally. The next-state functions are still affine, the polynomial is still recoverable — but the tap set no longer reads off the equations directly; you factor the matrix instead. Same tools, harder algebra.
  • Use the FSM tooling on something that has one. This design has no control FSM, so tools/hal_fsm and solve_fsm have nothing to nominate. Point them at a design with an actual state machine and compare what a transition-relation solve gives you against what SCC analysis alone gave you here.
  • Compose the claims instead of narrating them. tools/hal_explain reads the findings documents that DANA, module_identification and hal_fsm write and assembles a recovered-block model where every block's confidence is derived from the status of the finding that supports it. On a design this small a prose page is enough; on anything real, a machine-readable block model that cannot quietly promote a heuristic into a proof is the deliverable you want.
  • Read the findings, not the prose. Every analysis in this repository writes a tools/hal_findings document with an explicit status. artifacts/report.html renders the ones this walkthrough produced onto one offline page — that is the format an RE result should be delivered in, because it forces every claim to say how strong it is.
